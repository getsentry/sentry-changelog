Version 7.3.0 of the Sentry Ruby SDK is about the work your app does when nobody is watching: scheduled jobs, background jobs, and the feature flags that decide which code runs.

## Crons for GoodJob

If you schedule jobs with GoodJob's cron, Sentry can now monitor every entry without changes to your jobs. Enable the patch:

```ruby
Sentry.init do |config|
  config.enabled_patches << :good_job_cron
  # Optional: skip entries by key
  config.rails.good_job_exclude_cron_jobs = [:clear_cache, /\Atmp_/]
end
```

Sentry creates a monitor from each entry's key, schedule, and time zone. You get an alert when a job fails, runs too long, or does not start. This requires `good_job` 4.0 or later. See [Crons for Ruby](https://docs.sentry.io/platforms/ruby/crons/) for details.

## Feature flags on errors

Call `Sentry.add_feature_flag` each time your app evaluates a flag:

```ruby
Sentry.add_feature_flag("new-checkout", true)
```

Errors include the flags evaluated before them, and the active span records each evaluation. So when errors spike after a rollout, you can see which flags were on. See [Feature Flags](https://docs.sentry.io/platforms/ruby/feature-flags/).

## Queue latency for background jobs

ActiveJob, Sidekiq, and Resque jobs now report how long each job waited in the queue (`messaging.message.receive.latency`) and the size of its payload (`messaging.message.body.size`). Both show up in the [Queues](https://docs.sentry.io/product/dashboards/sentry-dashboards/backend/queues/) dashboard.

Under the hood, all job integrations now use one shared instrumentation layer. If you maintain a job backend, subclass `Sentry::JobExtensions::Extension` to get the same transactions, spans, and error reporting.

This release also stops recording credentials from Redis `AUTH` commands and supports the `Logger` block syntax in `Sentry.logger`. See the [release notes](https://github.com/getsentry/sentry-ruby/releases/tag/7.3.0) for all changes.
